# Household Inventory v1: Specification

What to build for v1, assembled from the decisions on the map [Household inventory system v1](https://github.com/anuarmusa/Inventory/issues/1). Each section links the ticket that holds the full reasoning. Terms in **bold capitals** (Supply, Batch, Action…) are defined in [GLOSSARY.md](../../GLOSSARY.md); use them as defined.

## 1. Goal and scope

One household tracks everything it owns: **Supplies** it uses up and restocks, and long-lived **Assets**. Android phones record changes by scanning, work offline away from home, and sync with a server on the home LAN. The server also hosts a web dashboard and the page where phones download the app.

**In v1**

- An Android app (no iPhone app).
- One **Household** with one shared inventory. **Devices** are tracked; people have no accounts.
- A home server, reachable only on the home Wi-Fi.
- Offline use with sync on return home.
- Barcode scanning for Supplies and QR **Labels** for Assets and **Locations**.
- **Low stock** and **Near expiry** **Alerts** worked out on each phone.
- Four reports: the Low-stock list, the Near-expiry list, total Asset value and the **Shopping list**.
- A web dashboard, a download page and a pairing flow.
- Label printing.

**Out of scope**

- Access from outside the house (VPN, port forwarding).
- User accounts and permissions.
- Spending reports. Purchase price is still recorded.
- Notifications from internet services.
- The Play Store and App Store.
- The iPhone app.

## 3. Data model

Source: [What exactly does each Supply, Batch, Asset and Location record?](https://github.com/anuarmusa/Inventory/issues/6).

- **Supply**: the general thing, whatever the brand (e.g. "Jasmine rice"). It has:
  - a name;
  - a unit chosen per Supply (pieces, packs, bottles), counted in whole units only;
  - a **Category** and a usual **Location**;
  - an optional **minimum** (at or below = Low stock) and an optional **restock-to** amount;
  - an optional Near-expiry window that overrides the household default of 7 days, or "doesn't expire".
- **Barcode**: belongs to exactly one Supply; a Supply can have many. It stores:
  - the brand, product name, pack size and photo;
  - **units added per scan**;
  - the source of its details (typed by the household, or Open Food Facts).

  Shop-weighed codes (13 digits starting `02` or `20`–`29`) never identify a Supply.
- **Batch**: a quantity of one Supply, with an optional expiry date and its own Location (defaulting to the Supply's usual one). Used **oldest first**: earliest expiry first, with undated Batches last.
- **Asset**: name, Category, Location, purchase date, price, shop, serial number, warranty end, photos, receipt photo and notes. It also has a log of **Maintenance entries** (date, note, cost). An Asset can be **Disposed** (date and reason) and stays in history. Total Asset value counts only Assets still owned.
- **Location** and **Category**: separate flat lists the household edits. Categories are shared by Supplies and Assets. Either can be deleted only when empty.
- **Label**: a random 5-character Label code linked to one Asset or Location, or a **Blank label** linked to nothing yet. A Label can be retired by Replace (see §10).
- **Device**: a name, a Device key, the app version it last reported, and when it last synced. A Device can be removed.
- **Mismatch**: the problem, the Action it came from, and its state (open, or resolved and how).
- Photos are stored as files on the server. Records refer to them by photo id.

Deleting a Supply or Asset is only for mistakes. It hides the record, keeps its history, and can be undone.

## 4. Actions and sync

Sources: [Design offline sync and how mismatched counts get fixed](https://github.com/anuarmusa/Inventory/issues/9) and [ADR 0001](../adr/0001-own-action-log-sync.md).

### 4.1 Actions

Every change is an **Action**: a domain intent, not a field write. Each Action carries:

- an id generated on the Device;
- the Device id;
- the Device's clock time;
- an action type;
- a shape version;
- a payload validated by a shared Zod schema.

Quantities are **deltas** ("used 2"), never absolute values, except a **Stocktake**. Actions are kept forever and make up the inventory's history.

Action types include:

- creating, editing and deleting a Supply, Asset, Location or Category;
- attaching or moving a Barcode;
- adding a Batch;
- using a Supply (Supply and amount only, with no Batch named);
- moving or discarding a specific Batch;
- a Stocktake;
- a **Merge**;
- moving an Asset, adding a Maintenance entry, or disposing of an Asset;
- attaching, replacing or retiring a Label;
- resolving a Mismatch;
- an **Undo** or a **Correction**.

### 4.2 Sync protocol

Sync is our own action log; it doesn't use a sync library.

- `POST /sync/push`: the Device sends its unsent Actions, its current clock time and its app version. The server works out the Device's clock offset from that time.
- `GET /sync/pull?since=<seq>`: returns everything changed since the Device's last server sequence number. The server keeps one sequence number that only ever goes up.
- Every response includes the latest app version the server hosts and the minimum app version it accepts (§9).
- Requests carry the Device key (§7). Unknown or removed keys are refused.

**The server is the source of truth.** The phone shows the last server state plus its own unsent Actions replayed on top. After a sync it drops the Actions the server accepted and takes the server's result, even if that differs from what it showed.

**When sync runs** (only while the app is open):

- when the app opens or returns to the foreground;
- after each Action while the server is reachable;
- from a "Sync now" button.

"At home" just means the server answers within a short timeout.

**Photos** sync separately. The file uploads when the phone is home; other Devices download it the first time it's viewed and cache it. An uncached photo shows a placeholder away from home.

**First run**: the app can't be used until it has paired and done one full sync at home.

### 4.3 How the server applies Actions

- Actions are applied in **arrival order**.
- A "used" Action takes from the oldest Batch at the moment it's applied. The server **records which Batches it took from**, so it can be undone (§5).
- **Stocktake** sets a Supply's total. If the count is lower than recorded, the difference comes off the oldest Batches. If it's higher, the extra becomes a new Batch with no expiry at the usual Location. A "used" Action whose corrected Device time is before the Supply's latest Stocktake is skipped, because the count already reflects it.
- Detail edits (name, minimum, Location…) are last-writer-wins by arrival, with no flag.

### 4.4 Mismatches

Sync always completes and never waits on a person. The server flags a **Mismatch** in three cases:

| Case | What the server does |
|---|---|
| A "used" Action would take a Supply below zero | Applies it down to zero and records the shortfall. |
| An Action on something Disposed or deleted | Skips the Action. |
| One Barcode (or one Blank label) attached to two different things | Keeps the first link. |

Open Mismatches appear as "Needs checking" in two places: a bar on the app's Home and a card on the web dashboard. Any Device or the dashboard can resolve one, and resolving is itself an Action. Resolved Mismatches stay in history.

| Mismatch | Fixes |
|---|---|
| Shortfall | **Count it** (a Stocktake), or **Accept** |
| Skipped Action | **Accept**, or redo it against something else |
| Barcode or Label on two things | Choose which one keeps it, or **Merge** the two Supplies |

**Duplicates**: two phones may create the same Supply while offline. Supplies with the same name get a "possible duplicate" hint, not a Mismatch, and are fixed with **Merge**, which moves the Batches and Barcodes into one Supply. Merge can't be undone, so it confirms first.

### 4.5 Versions

The server reads every older Action shape version it knows. Pushes are refused in two cases, and in both the Actions wait on the phone:

- **App too old** (below the minimum app version): the app shows "Update needed to sync".
- **Action shape the server doesn't know** (e.g. after a server rollback): the app shows "The home server is older than this app".

## 5. Undo and Correction

Source: [How does someone correct or undo a past Action?](https://github.com/anuarmusa/Inventory/issues/13).

History is never edited.

- An **Undo** is a new Action naming the original.
- A **Correction** is a new Action naming the original with the right values ("used 3, not 2"; "Milo, not rice").
- Unsent Actions are different: the phone can simply edit or drop them, leaving nothing in history.

What each Undo does:

- **Undoing "used"** puts the amount back into the exact Batches recorded at apply time, recreating any that were emptied.
- **Undoing "added a Batch"** removes what's left of that Batch. Any part already used becomes a shortfall Mismatch.
- **A later Stocktake wins**: undoing a quantity Action older than the Supply's latest Stocktake is recorded but doesn't change the amount. The app warns first: "Counted since: this won't change the amount."

What can be undone:

- Quantity Actions: Undo or Correction.
- Detail edits: just edit again.
- A Disposed Asset: Undo restores it.
- A Barcode on the wrong Supply: "Move barcode to…".
- Merge: can't be undone.
- Delete: can be undone.

Where it's done:

- From a **History** list on each Supply and Asset page.
- From **Recent activity** in the app and on the dashboard.
- From a short "Undo" toast after each Save in the scan flow.

Any Device can undo any Action, at any age. In history, the original is struck through with "Undone by Kitchen phone, 18 Nov" or "Fixed: 3, not 2".

Edge cases:

- Undoing the Action behind an open Mismatch closes that Mismatch ("resolved by undo").
- If two phones undo the same Action, the first to arrive applies and the second is skipped quietly.
- Undoing an Undo restores the original, and Corrections can chain.

## 6. App

### 6.1 Home

Source: [Prototype the app summary screen, web dashboard and download page](https://github.com/anuarmusa/Inventory/issues/15) (variant B). Prototype on the branch `prototype/dashboards`.

Top to bottom:

1. The title "Our home".
2. An update banner, when a new version is out.
3. A red "N need checking" bar, when Mismatches are open.
4. Three count tiles (**Low stock**, **Near expiry**, **To buy**). Each opens its list; To buy is a tick-off checklist showing the amount to buy.
5. A big **Scan** button.

Asset value isn't on the phone.

### 6.2 Scan flows

Source: [Prototype the scan flows](https://github.com/anuarmusa/Inventory/issues/10) (variant B with variant A's basket). Prototype on the branch `prototype/scan-flows`.

Scan is the single way in. What a scan opens depends on what was scanned:

- **A product Barcode** asks: "I bought some / I used some / Just show me".
- **A Label** opens the Asset or Location page, from anywhere, including in the middle of a basket (the basket waits).
- **A code that isn't ours** (e.g. a Wi-Fi QR) is refused with a message. A product not in the inventory can't be "used".

**I bought some: the shopping basket**

1. The camera stays open. Each later scan adds a line, and a repeat scan adds that Barcode's units-per-scan to its line, without asking again.
2. "Done scanning" moves on to one-question-per-screen steps, but only for lines that need them:
   - **New product**: the lookup result (§8), the name on the pack, which Supply it is (or a new one), and units per scan.
   - **Shop-weighed code**: which Supply it is.
   - **Expiry**, for Supplies that expire. Expiry is optional, with a big "No date on the pack" choice. **Split** gives part of a line a second date, making two Batches.
3. Quantity comes from scanning. Location defaults to the usual one and can be changed on the final basket review, before **Put away**.

**I used some**

1. It asks how many, in the Supply's own unit, defaulting to 1 (e.g. 1 roll from a 10-roll pack).
2. It shows that the oldest Batch goes first and how many will be left.
3. **Save** confirms it, and a short Undo toast follows.

### 6.3 Asset, Location and Supply pages

- **Asset page**: all details, photos, the maintenance log and History. It offers **Move**, **Log maintenance** and **Dispose** (with a reason). A Disposed Asset still opens, shown as Disposed.
- **Location page**: the Batches and Assets kept there, and **Count what's here** (Stocktake).
- **Supply page**: amount on hand, its Batches (expiry and Location), Barcodes, minimum, restock-to and History.

### 6.4 Labels in the app

Scanning a **Blank label** offers "Attach to: a new Asset / an existing Asset / a Location". This works offline as an Action. An Asset or Location without a Label shows "No Label yet". Scanning a retired Label says "This Label was replaced".

### 6.5 Alerts

Each Device works out Low stock and Near expiry from its local data using the shared rules, and schedules local notifications with `expo-notifications`. It doesn't depend on the server. Alerts arrive as one daily summary at 09:00 (§13).

## 7. Pairing and Devices

Sources: [How does a phone find and pair with the home server?](https://github.com/anuarmusa/Inventory/issues/11), with the HTTP correction from [Deployment design](https://github.com/anuarmusa/Inventory/issues/12).

- The server has a **reserved LAN IP**. There's no network discovery; the app learns the address at Pairing. If the address changes, pair again.
- **Pairing**: the download page offers the server address and a **one-time code** that expires after 10 minutes. The app redeems it; the server records the Device and returns a long-lived **Device key**, which the app sends with every request. There are three ways to receive the pairing offer:
  1. a **"Connect this phone"** button on the download page, which opens the app through a link (`inventory://pair?…`);
  2. a **QR code**, scanned from the app's "Connect at home" screen;
  3. **typing** the address and a 6-digit code.
- **Trust**: anyone on the home Wi-Fi can pair a phone and open the dashboard. There's no PIN; visitors belong on the router's guest network.
- **Plain HTTP** on the LAN. The APK allows plain HTTP for all addresses, because Android fixes that rule when the APK is built; the app only ever sends HTTP to the paired server. HTTPS is a possible later upgrade.
- **Device names**: the app suggests the phone model and the household can rename it ("Kitchen phone"). The name appears in the Device list and in history. It labels a phone, not a person.
- **Remove** makes a Device's key stop working. A removed phone shows "This phone was removed. Connect again." Reconnecting the same install keeps its unsent Actions. A reinstall or a new phone is a new Device.

## 8. Barcode lookup

Source: [Can scanned barcodes fill in product names automatically?](https://github.com/anuarmusa/Inventory/issues/5).

1. The household's own Barcodes come first. They work offline.
2. On the first scan of an unknown Barcode while the phone has internet, the app looks it up on Open Food Facts directly from the phone (no API key; allowed rate 15 lookups/min).
3. Otherwise the details are typed by hand.

When Open Food Facts details are used, show the attribution "Product data © Open Food Facts contributors (ODbL)", and record the Barcode's source as Open Food Facts.

## 9. App updates

Source: [How does a phone learn a new app version is out and install it?](https://github.com/anuarmusa/Inventory/issues/14).

- Sync responses carry the latest hosted version and the minimum accepted version. There's no separate polling.
- **When a new version is out**, Home shows a dismissible banner, "Update available: v1.4", with the one-line what's new.
- **When the app is below the minimum**, a red "Update needed to sync" banner shows instead. The app keeps working offline, and sync waits.
- **Update** does three things:
  1. It syncs first, if the server still accepts this version.
  2. It downloads the APK from the home server.
  3. It opens Android's installer. The first time, Android asks to allow "Install unknown apps" for Inventory.

  Every APK is signed with the same key, so the update installs over the old app and its data, including unsent Actions, survives. The download page is the fallback.
- **The minimum version** is a constant in `packages/shared`. It's raised only when older apps would send Action shapes the server can no longer read, or must not sync.
- **Visibility**: each Device reports its app version with every sync, and the Device list flags out-of-date Devices.

## 10. Web

### 10.1 Dashboard

Source: [Prototype the app summary screen, web dashboard and download page](https://github.com/anuarmusa/Inventory/issues/15) (variant A).

One screen with three parts:

- **Needs checking** card across the top, only when Mismatches are open, each with its fix buttons.
- **A 2×2 grid of the four reports:**
  - **Shopping list**: amounts to buy, with tick boxes;
  - **Near expiry**: each Batch with its date and "in N days";
  - **Low stock**: amount on hand against the minimum;
  - **Assets**: prices, and the total for Assets still owned.
- **Recent activity sidebar**: the Device, the time, and Undo.

A footer on every web page shows the **server version** and the **time of the last backup**, in a red badge if the backup failed.

The dashboard also hosts editing the inventory, Location and Category lists, and Label printing (§10.3).

### 10.2 Download page

Source: same ticket (variant A). It's a single column that works at phone width, because it's usually opened on the phone:

1. **Download the app**: the version, the date, what's new, and a Download APK button.
2. **Install it**: a hint about allowing the browser to install unknown apps.
3. **Connect this phone**: the button. The QR, server address and 6-digit code sit under "Using another screen? Scan a code instead".

Below the steps, **Phones connected** is a table with each Device's name, model, app version (with an "Out of date" badge), last sync time and a Remove button.

### 10.3 Label printing

Source: [How are Labels printed?](https://github.com/anuarmusa/Inventory/issues/16).

- **QR content**: `INV1:<code>`, where `INV1` marks our Labels and their format version, and `<code>` is a random 5-character Label code. It's neither a URL nor a database id.
- **What's printed**:
  - an assigned Label gets the QR, the thing's name and the code in small print;
  - a Blank label gets the QR and the code;
  - the Location isn't printed.
- **Stock**: A4 sticker sheets with 21 labels each, 63.5 × 38.1 mm (QR about 30 mm). Paper for indoors; waterproof vinyl for the freezer, fridge, garage and outdoors. The dashboard generates a **PDF** for any printer, with no printer integration.
- **Where printing starts** (dashboard only; phones don't print in v1):
  - "Print Labels for N new things" (everything showing "No Label yet");
  - a print option on any Asset or Location;
  - "Print a sheet of blank Labels".

  The print dialog asks "Start at label position N" and shows a sheet map, to reuse partly used sheets.
- **Lost or damaged Labels**:
  - **Reprint** prints the same code, and the old Label keeps working.
  - **Replace Label** links a new code and retires the old one.

## 11. Deployment and operations

Source: [Deployment design](https://github.com/anuarmusa/Inventory/issues/12).

- **Containers**: `app` (Fastify: API, web, APKs) and `db` (Postgres), in one `compose.yaml` with a dev override. Both use `restart: unless-stopped`. Server data lives in `/srv/inventory/` (db, photos, apk, backups).
- **Network**:
  - port 80 on the server and 8080 on the dev PC;
  - ufw allows only port 80 and SSH, only from the LAN;
  - the IP is reserved in the router.
- **Configuration**: an uncommitted `.env` (database password, `TZ=Asia/Kuala_Lumpur`, an optional public address) and a committed `.env.example`. The address in pairing offers comes from the address the page was opened with, unless that setting overrides it.
- **Deploying** with `pnpm run deploy` on the dev PC:
  1. bumps the Android version code and sets the visible version;
  2. asks for a one-line "what's new";
  3. builds the APK and writes `latest.json` next to it;
  4. builds the Docker image;
  5. copies the image with `docker save | ssh server docker load`;
  6. copies the APK to `/srv/inventory/apk/`;
  7. runs `docker compose up -d`.

  There's no registry and no git on the server.
- **On start**, `app` takes a backup, then applies pending Drizzle migrations, then starts serving. A failed migration stops the container.
- **Backups**:
  - nightly at 03:00, `pg_dump` plus the photos folder, kept 14 days;
  - copied to a USB drive on the server, with the dev PC pulling a copy as a fallback;
  - restored with `scripts/restore.sh <backup>`, given a test run during first setup.
- **Rollback**: images are tagged by version and the last two are kept. `scripts/rollback.sh` starts the previous image, first restoring the pre-migration backup only if the bad version ran a migration. Actions synced since that backup are lost from the server.
- **APK signing**: one release key, made once and kept on the dev PC outside the repo. Its password goes in the password manager, and a copy is stored with the off-server backups. Losing it forces an uninstall on every phone.
- **Logs and health**: Docker logs are capped at 10 MB × 3 per container. A `/health` endpoint backs the Compose healthcheck.
- **Development**:
  - Postgres runs in Docker Desktop, and server and web run with `pnpm dev`;
  - a Windows Firewall rule for private networks lets phones reach the dev PC;
  - `docker compose up` on the dev PC is the production-like check.
- **First server setup** is delivered as a step-by-step wizard script: the router IP reservation, installing Docker, `/srv/inventory`, ufw, the SSH key, the backup drive, the first deploy and a test restore.

## 13. Defaults chosen while drafting

These details weren't decided on the map. They were settled when this spec was drafted:

1. **When Alerts fire**: one local notification a day at 09:00, summarising new Low stock and Near expiry items, rather than one notification per item.
2. **Shopping list amount without restock-to**: for a Supply with a minimum but no restock-to, the amount to buy is the minimum + 1 − on hand.
3. **Editing Supplies, Assets, Locations and Categories in the app**: simple forms on the Supply and Asset pages and a Settings screen for the lists, mirrored on the dashboard.
4. **Photo size**: photos are resized to 1600 px on the long edge before upload.
